# Perth Brickwork

A config-driven static site for Perth bricklaying lead generation
(rank-and-rent). Plain HTML/CSS/JS — no build step, no framework, no
external fonts. Designed for GitHub Pages with a custom domain.

Content source: **"Perth Brickwork — Page Copy v6"**. Five pages:

| URL | Targets |
|---|---|
| `/` | `bricklayer perth` (500/mo) |
| `/brick-repairs-repointing-tuckpointing` | `tuckpointing perth` (500/mo, low comp), `federation tuckpointing perth`, `tuckpointing perth cost` |
| `/brick-fences-boundary-walls` | `brick fence cost perth` (50/mo) — **gated, see below** |
| `/about` | disclosure: who runs it, how it's paid |
| `/privacy` | what the form collects and who it goes to |

## Read this before publishing anything

The copy is full of `[VERIFY: ...]` and `[NEEDS INPUT: ...]` markers. They
render on the page as loud amber "unfinished — not for publication" boxes,
and `node bake.js --check` **fails while any of them remain**. That is the
point. Nothing here may state a price, a council figure, a mortar spec, a
suburb claim, a registration threshold, a date or a credential that hasn't
been sourced.

For each marker: fill it from a real source, or delete the claim it guards.
**Never just remove the marker.**

Two gates worth knowing about:

- **The fences page must not go live until the per-council fence table is
  populated.** Without that table it's a service page competing on one
  50/mo cost term, which is thin. Nobody else in the market publishes the
  table, which is the whole reason the page is worth building.
- **v6's publishing order is homepage + repairs page first**, together.
  The about page can ship with them. Fences comes second.

**Swapping niche/city: edit [`config.js`](config.js), run `node bake.js`,
run `node bake.js --check`, commit the regenerated files.** `config.js` is
the only file you edit by hand — everything else is regenerated from it.
`bake.js` is a manual helper you run yourself — not a build pipeline;
nothing runs automatically and the deployed site stays plain static files.

## How it works

At load time, `js/main.js` reads `window.SITE_CONFIG` from `config.js` and
renders each page body from an ordered array of typed **blocks**, plus brand
colors and the GA4 snippet. Each content page is mapped to an entry in
`services` by its `page` field; each area page is mapped by its `slug` (the
file is `<slug>.html`).

**Block types** (see the comment above `services` in `config.js`):

| Block | Renders |
|---|---|
| `{ h2 }` `{ h3 }` | headings — a new `h2` starts a new banded section |
| `{ p }` `{ lead }` | paragraph(s); string or array of strings |
| `{ ul }` `{ ol }` | lists |
| `{ table: {columns, rows} }` | data table, scrolls horizontally inside its own box |
| `{ note }` | quiet callout |
| `{ credit }` | author / sourcing line under the H1 |
| `{ marker }` | **unfinished-work box** — `--check` fails while any exist |
| `{ faqs: [{q,a}] }` | FAQ accordion, and feeds the page's FAQPage schema |
| `{ form: {...} }` | the enquiry form |

Text in any block supports `**bold**`, `[label](url)` and newlines. Escaping
happens before that markup is re-enabled, so config copy can't inject HTML.

**Schema is `Organization` only, sitewide.** Deliberately *not*
`LocalBusiness`: there's no premises, no opening hours and no service
counter, so those properties would be absent or invented. No
`AggregateRating` and no `Review` either — there are none. `--check` fails
if any of them reappear in the baked HTML. Revisit only when a renter's real
details are on the site.

**What's baked into static HTML (for SEO — crawlers see it before any JS
runs):** each page's `<title>`, meta description, canonical URL, Open Graph
tags, JSON-LD (Organization on every page; FAQPage built from the `faqs`
blocks actually on that page; Service + BreadcrumbList on the two content
pages; AboutPage + Person on about; BreadcrumbList on privacy), the H1, and
the `<noscript>` fallback.

**The phone number degrades safely.** While `business.phone` holds the
`[PHONE]` placeholder, every `tel:` link is suppressed rather than rendered
dead — the header call button and the form's error fallback simply don't
appear, and `telephone` is omitted from the schema.

**Everything derived is regenerated by one command:**

```
node bake.js
```

That rewrites all page HTML **plus** `CNAME`, `robots.txt`, `sitemap.xml`
(built from the actual list of pages generated, so it can never drift),
`404.html` (name/phone from config), and `favicon.svg` (brand color from
config). The only static asset it doesn't generate is `images/og-image.png`
— a neutral illustration containing no business details, so it doesn't
need changing per niche (replace it with a real photo if you have one).

**Before launch, run the preflight:**

```
node bake.js --check
```

It writes nothing and fails loudly (exit 1). It reports two classes of
problem separately:

- **Unfinished content** — every `[VERIFY]`, `[NEEDS INPUT]`, `[BUILD GATE]`
  and `[PLACEHOLDER]` still in config, and every `{ marker }` block. Listed
  with its config path so you can find it. This is the launch blocker.
- **Preflight problems** — leftover template placeholders, unset
  tracking/form IDs, missing or orphaned page files, sitemap/disk drift,
  domain mismatch, missing images or image dimensions, duplicate meta
  title/description, and banned schema types leaking into the baked HTML.

Warnings (non-fatal) fire if `testimonials`/`photos` are populated — a
reminder that those must only ever contain real content.

## Editing checklist

1. Edit `config.js` (all the content lives there, top to bottom — details
   below).
2. Run `node bake.js` to regenerate every derived file (pages, CNAME,
   robots.txt, sitemap.xml, 404.html, favicon.svg).
3. Run `node bake.js --check` and fix everything it flags.
4. Commit the regenerated files.

What to edit in `config.js`:

1. **business** — name, phone (both `tel:` and display format), city, state,
   service area, ABN, registered business name. `email` is blank: v6's
   footer and contact block list no email, and the footer omits it while
   it's empty.
2. **domain** — used for canonical URLs, schema, OG tags, and to generate
   `CNAME`, `robots.txt`, and `sitemap.xml`. You never edit those three by
   hand.
3. **brand** — accent color, a darker hover shade, and the text color used
   on top of the accent. The favicon is generated from these. Also pick the
   visual theme here (`style` + `pattern`) — see "Making each site look
   different" below.
4. **ga4Id** — your GA4 measurement ID. **Required before launch**: while it
   contains `XXXX`, the tracking snippet is not injected, so you get no
   analytics and no `click_to_call` events — meaning no call-volume proof
   to show a future renter. (The placeholder is safe to develop with.)
5. **formspreeId** — create a free form at [formspree.io](https://formspree.io),
   copy the ID after `/f/` in the endpoint. **Required before launch: the
   site cannot capture web form leads until this is a real ID.** Until
   then, submitting the form shows a polite error — phone calls work (once a
   real number is in), web leads are silently lost.
6. **schema** — legal name, the ABN used as the Organization `identifier`,
   area served, and the founder name used on the about page's `Person`.
   Don't reintroduce a `LocalBusiness` type here; `--check` will reject it.
7. **pages** — meta titles/descriptions and headlines for home, about and
   privacy. Make each headline mirror the exact search phrase the page
   targets.
8. **form** — the shared enquiry form: field list, submit text, the line
   under the button, and the success/error messages. Pages override the
   preset, per-field placeholders, and may insert an extra field (the
   repairs page adds "Roughly how old is the building?"). Changing the field
   list means updating `privacyBlocks` to match — the privacy policy
   describes the actual fields.
9. **services** — the two long-form content pages. Each maps to a keyword
   URL via its `page` field; the sitemap follows automatically. The page
   body is its `blocks` array.
10. **areas** — suburb pages. Deliberately empty. v6 rules them out until
    the core pages are live *and* each suburb page has genuinely
    differentiated content; `bricklayers joondalup` is real but only 50/mo.
    An unsupported suburb list is the scaled-content pattern to avoid.
11. **homeBlocks / aboutBlocks / privacyBlocks** — the bodies of the
    homepage, about page and privacy policy.
12. **images** — a hero via `image:` on `pages.home` / a service entry, and
    inline ones via `{ image: {...} }` blocks anywhere in a body.
    - Use optimized **JPG or WebP**, ~1000px wide, under ~150KB (there's no
      build step, so optimize before committing — e.g.
      [squoosh.app](https://squoosh.app)).
    - Keep `width`/`height` accurate to prevent layout shift; `--check`
      fails on a missing file or missing dimensions.
    - Write `alt` text that literally describes what is depicted.
    - `images/og-image.png` stays — a neutral illustration with no business
      details on it, used only for link previews.

### The images currently on the site are illustrative

They are **not** photographs of work done by Perth Brickwork or by any
bricklayer it refers to, and nothing on the site says or implies they are.
That is why they carry **no captions**, and why `photos` — the "Recent Work"
section — is still empty. That section is the one that would claim
authorship, and it stays empty until a renter supplies real, verifiable job
photos.

Two placement rules follow from that, and both are load-bearing:

- **Nothing illustrative goes in the crack-diagnosis section** of the
  repairs page. That section teaches a reader to tell a maintenance crack
  from a movement crack. An image there has to show a real failure or it
  misleads someone deciding whether to call an engineer. The `[NEEDS INPUT]`
  marker on that section stays open.
- **The retaining-vs-level diagram on the fences page has to be drawn**, not
  sourced. It explains a distinction rather than decorating a section.

The source PNGs (`hero678ty4.PNG` and friends) are still in `/images` and
are no longer referenced — safe to delete, and worth deleting before you
push, since they're ~2MB each.

## Making each site look different

Every deployment can have its own look without touching CSS. Three knobs in
`config.js` combine into the theme, and everything else (tints, glows,
shadows, the footer color, even the favicon shape) is derived automatically:

1. **`brand.color` / `colorDark` / `colorContrast`** — the palette. One
   accent color drives the whole site: pale section washes, tinted borders,
   colored button shadows, and a matching dark footer are all computed from
   it by `bake.js` (and re-derived at load time by `js/main.js`).
2. **`brand.style`** — the design personality:
   - `classic` — clean and trustworthy; soft gradient hero, rounded cards
   - `bold` — full-color gradient hero with a diagonal edge, pill buttons,
     heavy headings
   - `soft` — heavily rounded corners, pale tinted sections, blob-shaped
     imagery, rounded font (where the OS has one)
   - `sharp` — squared corners, hard borders, offset solid shadows,
     uppercase section headings
   - `elegant` — serif display headings, framed imagery, thin rules, quiet
     and premium
3. **`brand.pattern`** — a subtle background texture on the hero, page
   headers, and CTA band: `none`, `dots`, `grid`, `diagonal`, or
   `crosshatch`. Patterns are pure CSS gradients (zero requests) and adapt
   automatically to light and colored backgrounds.

The chosen style/pattern is baked onto the `<html>` tag and the derived
palette into each page's `<head>` by `node bake.js`, so the final look
renders on first paint with no flash and no JS required for styling.
`bake.js` (and `--check`) validate the values and fail loudly on typos.

None of this affects SEO: titles, meta, schema, H1s, and the noscript
fallback are baked exactly as before, there are still no external fonts or
requests, and all motion (scroll reveals, hover lifts) is CSS/JS that
respects `prefers-reduced-motion` and degrades to fully-visible static
content when JavaScript is off.

A quick way to pick a combination: temporarily change `style`/`pattern` in
`config.js` and reload your local preview — `js/main.js` applies the config
values live, so you can flip through looks before baking.

## Real-evidence placeholders (do not fake these)

`testimonials` and `photos` in `config.js` are **intentionally empty**. The
"What Customers Say" and "Recent Work" sections exist in the template but
stay hidden until these arrays contain real, verifiable content from an
actual operating business. Never populate them with invented names, star
ratings, or review counts — that's a legal/ethical liability (FTC fake
review rules) and gets renters angry when discovered.

## When a renter signs

Several markers are deliberately left open pending a real bricklayer renter,
because their real pricing and practice is a better source than anything
pre-collected. Work through this list once one signs:

- **Pricing tables** (repairs page and fences page, `services[0]` /
  `services[1]` `blocks`, the "What tuckpointing and repointing cost in
  Perth" / "What a brick fence costs in Perth" sections) — there is no table
  there now, deliberately: an earlier placeholder table full of `[VERIFY]`
  cells was removed in favour of the honest paragraph that's there instead,
  because a table with no real data in it looks broken, not "coming soon."
  Add a real table once the renter's own rates exist. Log each figure with
  the date, suburb, job type, area or joint length, building age, access and
  whether scaffold was required. Never a competitor site or a national
  average.
- **`testimonials` / `photos`** — see "Real-evidence placeholders" above.
- **Schema** — `LocalBusiness`, `AggregateRating` and `Review` stay off
  (`--check` rejects them) until the renter's real details are on the site
  and any reviews are genuinely theirs.

Run `node bake.js --check` after each of these — the count of remaining
markers is the honest measure of how much is left before launch.

## Deploy to GitHub Pages

1. Create a public repo and push all files to the root of the default branch.
2. Repo → Settings → Pages → Source: "Deploy from a branch" → your default
   branch, `/ (root)`.
3. Custom domain: put your bare domain in `CNAME` (GitHub fills the Pages
   setting from it), then point DNS at GitHub Pages:
   - `A` records for the apex: `185.199.108.153`, `.109.153`, `.110.153`, `.111.153`
   - `CNAME` record for `www` → `<username>.github.io`
4. Enable "Enforce HTTPS" once the certificate is issued.
5. Submit `sitemap.xml` in Google Search Console.

## Local preview

Any static file server works, e.g.:

```
npx serve .
# or
python -m http.server 8080
```

(Opening files via `file://` won't work reliably — the pages fetch nothing,

## Divergence from the original template

This started as the generic lead-gen template (`New site prompt.txt`
describes that workflow, and says not to change the engine). v6's copy
didn't fit it, so the engine was extended deliberately:

- The card/`included`/`priceNote` service layout was replaced with the block
  renderer, because v6's pages are long-form prose with data tables.
- `faq.html` was removed; v6 puts FAQs on the page they belong to, and the
  FAQPage schema is now built from those blocks.
- The five generic `service-N.html` stubs were deleted in favour of two
  keyword URLs.
- `LocalBusiness` became `Organization` — see "How it works" above.
- The two-step name/phone form became the seven-field qualifying form.
- `--check` grew the marker class of failure.

If you ever regenerate from the upstream template, these changes need
re-applying.
